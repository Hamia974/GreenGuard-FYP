# Integration Guide — Module 3: Weather Risk Engine

**For: Backend (Django) team**

## How to call this service

- **Method:** POST
- **URL:** `http://localhost:8001/predict` (dev) — replace host/port for staging/production once deployed
- **Content-Type:** application/json

### Request body
```json
{
  "latitude": 31.5204,
  "longitude": 74.3587,
  "farm_id": "farm_001"
}
```
`farm_id` is optional — if omitted, it defaults to `"unknown"` and is simply echoed back.

### Success response — HTTP 200
```json
{
  "farm_id": "farm_001",
  "timestamp": "2026-09-01T22:39:35Z",
  "weather": {
    "temperature": 28.0,
    "humidity": 78.0,
    "rainfall_last_7_days_mm": 1.8,
    "wind_speed": 2.2
  },
  "units": {
    "temperature": "celsius",
    "humidity": "percent",
    "rainfall_last_7_days_mm": "mm",
    "wind_speed": "m/s"
  },
  "risk_assessment": {
    "fungal_disease_risk": "Moderate",
    "fungal_disease_reason": "Humidity is 78%, above the 65% threshold that raises fungal risk, though today's temperature/humidity combination isn't in the high-risk range.",
    "heat_stress_risk": "Low",
    "heat_stress_reason": "Current temperature (28.0°C) is at or below 35°C and no recent day averaged above that threshold.",
    "drought_risk": "High",
    "drought_reason": "Only 1.8mm of rain fell in the last 7 days, below the 10mm high-drought threshold."
  },
  "forecast": {
    "temperature": 31.5,
    "humidity": 63.5,
    "rainfall_mm": 2.0
  },
  "predicted_risk_assessment": {
    "fungal_disease_risk": "Low",
    "fungal_disease_reason": "Humidity (63.5%) is below the 65% risk threshold and no day in the last 3 was fungal-conducive.",
    "heat_stress_risk": "Low",
    "heat_stress_reason": "Current temperature (31.5°C) is at or below 35°C and no recent day averaged above that threshold.",
    "drought_risk": "High",
    "drought_reason": "Only 3.8mm of rain fell in the last 7 days, below the 10mm high-drought threshold."
  }
}
```
This is a real, live-captured response (model weights unchanged since v1.9.0; the response contract and error handling have moved on to v1.12.0 — see MODEL_DOCUMENTATION.md's changelog), not a fabricated example.

`fungal_disease_reason` / `heat_stress_reason` / `drought_reason` (v1.7.0) are always present alongside their matching `*_risk` label, in both `risk_assessment` and `predicted_risk_assessment` — a full sentence naming the specific threshold/value that produced that label. Safe to show directly to a user; do not parse them for logic, since wording may change between versions while the `*_risk` values will not.

`forecast` and `predicted_risk_assessment` come from an LSTM add-on (v1.6.0, see MODEL_DOCUMENTATION.md) and are **nullable** — both come back as `null` if the model can't produce a prediction for any reason. Never assume they're present; check for `null` before reading them. `risk_assessment` (current conditions) is unaffected either way and is always populated on a 200 response.

### Error responses
| Status | When | Body |
|---|---|---|
| 422 | latitude/longitude missing, wrong type, or out of range (-90 to 90 / -180 to 180) | FastAPI's default validation error: `{"detail": [{"type": ..., "loc": [...], "msg": ...}, ...]}` |
| 500 | Open-Meteo weather API unreachable, rate-limited past retries, returned implausible data, or another internal failure | `{"message": "<description>"}` — always the `message` key. For the weather-unavailable case specifically, the value is `"Prediction Failed: weather service unavailable."`; for other unexpected failures it's just `"Prediction Failed"`. Branch on the presence of a 500 status, not on the exact string. |

**Verified during final review:** earlier in this module's development, the weather-unavailable 500 case actually returned `{"detail": "..."}` instead of `{"message": "..."}`, due to FastAPI's built-in `HTTPException` handler silently overriding the app's own error formatting. That's fixed now (v1.10.0) — every 500 uses the `message` key shown above. If your Backend error handling was already written against `detail` for this endpoint, update it to `message`.

## Health check

`GET /health` → `{"status": "ok", "service": "weather-risk-module"}` — use this for uptime monitoring / readiness checks.

## What Backend should NOT do

- Do not recalculate or modify `risk_assessment` values — store and forward them as-is.
- Do not rename any field before storing or returning to frontend.
- Do not treat `forecast` / `predicted_risk_assessment` as always-present — they're nullable by design.
- Do not parse `*_reason` strings for logic (e.g. regexing out a number) — they're for display, and wording may change between versions. Branch on `*_risk` (Low/Moderate/High) instead.
